# ДЗ 5. Сохраненная карточка: просмотр и редактирование

## Задача

Создайте небольшое приложение, в котором пользователь заполняет форму и получает сохраненную тематическую карточку.

Это не повтор семинарской заявки. На практике данные возвращались в те же поля формы. В домашней работе нужно самостоятельно организовать три состояния интерфейса:

1. **Пустое состояние** — сохраненной карточки пока нет.
2. **Редактирование** — пользователь заполняет или изменяет форму.
3. **Просмотр** — форма скрыта, на странице показана сохраненная карточка.

Переходы должны работать так:

```text
пустое состояние
       ↓ создать
редактирование
       ↓ сохранить
просмотр карточки
       ↓ редактировать
редактирование с сохраненными значениями
       ↓ сохранить
обновленная карточка

просмотр карточки → удалить → пустое состояние
```

После перезагрузки страницы сохраненная карточка должна открываться сразу в режиме просмотра.

Основное время должно уйти на проектирование данных, JavaScript, проверку переходов и исправление ошибок. Отдельное ТЗ, отчет о процессе и большой чек-лист писать не нужно.

## Основная часть — до 5 баллов

Основная часть — это законченная работа, а не набор строк по образцу. Нужно самостоятельно выбрать поля, собрать объект, определить состояния интерфейса и решить, когда данные записываются, читаются и удаляются.

### 1. Форма и модель данных — до 0,75 балла

Добавьте в `project/index.html` не менее четырех осмысленных полей для выбранной темы.

Требования:

- каждое поле отвечает за отдельное свойство будущей карточки;
- у каждого элемента есть связанный `label`, уникальный `id` и понятный `name`;
- используются минимум три разных вида элементов или типа ввода;
- обязательные значения отмечены через `required`;
- применено хотя бы одно содержательное ограничение: например, `minlength`, `type`, `min`, `max` или обязательный выбор;
- кнопка сохранения отправляет форму, остальные кнопки не отправляют ее случайно.

Готовая схема полей не выдается. Поля должны подходить выбранной теме, а не повторять заявку участника с семинара.

Проверка: браузер останавливает пустые и явно некорректные значения, а корректная форма доходит до обработчика `submit`.

### 2. Получение данных — до 0,75 балла

В `project/script.js`:

- найдите нужные элементы страницы;
- подпишитесь на `submit` формы;
- остановите стандартную перезагрузку через `preventDefault()`;
- создайте `FormData` внутри обработчика;
- получите значения по их `name`;
- соберите один объект карточки с понятными свойствами.

Объект не должен содержать вручную вписанные демонстрационные значения. Повторная отправка формы должна собирать актуальные данные.

Проверка: измените все поля и отправьте форму еще раз. В объекте должны оказаться новые значения.

### 3. Три состояния интерфейса — до 1 балла

Реализуйте переходы между пустым состоянием, формой и просмотром карточки.

Обязательное поведение:

- кнопка создания открывает пустую форму;
- корректная отправка скрывает форму и показывает карточку;
- карточка выводит все сохраненные значения через DOM;
- кнопка редактирования возвращает значения в форму;
- повторное сохранение обновляет существующую карточку;
- кнопка удаления возвращает пустое состояние;
- одновременно виден только один основной режим.

Не вставляйте пользовательские значения через `innerHTML`. Для текста используйте `textContent`, а видимость меняйте через `hidden` или CSS-класс состояния.

Проверка: создайте карточку → отредактируйте минимум два поля → сохраните снова → удалите. На каждом шаге интерфейс должен показывать правильное состояние.

### 4. JSON и `localStorage` — до 1 балла

Самостоятельно выберите постоянный ключ хранилища.

Нужно:

- превратить объект карточки в строку через `JSON.stringify`;
- сохранить строку в `localStorage`;
- при загрузке страницы проверить наличие данных;
- восстановить объект через `JSON.parse`;
- сразу показать восстановленную карточку в режиме просмотра;
- при удалении убрать запись через `removeItem`;
- не вызывать `JSON.parse`, если записи нет.

Проверка:

1. Создайте карточку.
2. Найдите JSON во вкладке Application.
3. Перезагрузите страницу — должна открыться карточка, а не пустая форма.
4. Удалите карточку и перезагрузите страницу снова — старые данные не должны вернуться.

### 5. Осмысленный `sessionStorage` — до 0,5 балла

Используйте `sessionStorage` для временной задачи, отличающейся от постоянной карточки.

Подходящие варианты:

- незавершенный черновик редактирования;
- текущий режим интерфейса;
- признак уже показанной подсказки;
- другое временное состояние, которое имеет смысл только в текущей вкладке.

Нельзя просто записать в `sessionStorage` ту же строку под тем же ключом, что и в `localStorage`, и назвать это отдельной функцией.

Проверка: покажите обе записи в DevTools и объясните, зачем каждая существует и когда должна исчезнуть.

### 6. HTML, CSS и БЭМ — до 0,5 балла

- новые классы продолжают структуру стартового проекта;
- блоки, элементы и модификаторы названы последовательно;
- разметка формы остается семантической;
- для состояний не добавляются случайные встроенные стили;
- страница остается читаемой после добавления полей и длинных значений.

БЭМ оценивается в основной части, потому что это уже знакомый рабочий навык. При этом оформление не должно занимать больше времени, чем логика приложения.

## Дополнительная часть — до 5 баллов

Сначала завершите основной сценарий. Бонус начисляется только за работающий и понятный результат, который не ломает базовую часть.

Дополнительные баллы разделены на три уровня. Это ограничение сделано специально: 10 баллов нельзя набрать только большим количеством простых улучшений.

### Уровень A. Развитие на знакомых инструментах — до 2 баллов

#### A1. Коллекция карточек — +1,5 балла

- в `localStorage` хранится массив объектов;
- можно добавить несколько карточек;
- коллекция восстанавливается после перезагрузки;
- отдельную карточку можно открыть, изменить и удалить;
- изменение не создает дубликат;
- для пустой коллекции есть отдельное состояние.

#### A2. Зависимая валидация — +1 балл

Добавьте одно правило, зависящее от нескольких значений или смысла темы. Например, дата окончания не может быть раньше даты начала.

- после исправления сообщение исчезает;
- корректные значения не блокируются;
- еще один `required` или `minlength` не считается зависимой валидацией.

#### A3. Автосохранение черновика — +0,5 балла

- незавершенные значения сохраняются по `input` или `change`;
- черновик восстанавливается отдельно от подтвержденной карточки;
- пользователь видит наличие черновика;
- незавершенный ввод не перезаписывает подтвержденную карточку.

#### A4. Свое прикладное расширение — до +1 балла

Можно добавить другой законченный сценарий на знакомых инструментах. Смена цвета, дополнительная подпись или еще одно однотипное поле бонусом не считаются.

За весь уровень A начисляется не более 2 баллов.

### Уровень B. Самостоятельное исследование — до 2 баллов

Здесь нужно самостоятельно открыть документацию, разобраться с новым механизмом и суметь его объяснить. Один результат нельзя одновременно заявить как A2 и B4.

#### B1. Импорт и экспорт файла JSON — +1,5 балла

- приложение создает файл с актуальными данными;
- пользователь может выбрать файл и импортировать его обратно;
- данные проверяются до записи в хранилище;

Справка: [Blob](https://developer.mozilla.org/en-US/docs/Web/API/Blob).

#### B2. Синхронизация вкладок — +1,5 балла

- интерфейс не создает цикл обновлений;
- студент может объяснить, в какой вкладке возникает событие `storage`.

Справка: [событие storage](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event).

#### B3. Отложенное автосохранение — +1 балл

#### B4. Constraint Validation API — +1 балл

- используется содержательное правило через `setCustomValidity()` или связанный механизм;
- сообщение сбрасывается после исправления значения;

- студент может объяснить отличие от обычной проверки внутри `if`.

Справка: [Constraint Validation API](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Constraint_validation).

#### B5. Срок жизни данных — +1 балл

Перед началом коротко согласуйте идею и способ проверки с преподавателем. Отдельный отчет писать не нужно.

### Уровень C. Целостность решения — +1 балл

Этот балл доступен только при наличии работающего результата и из уровня A, и из уровня B.

Частично выполненная самостоятельная работа оценивается по критериям. Неполный объем сам по себе не является основанием для 0 баллов.

## Использование ИИ

ИИ можно использовать как консультанта, но не как автора работы.

Можно:

- попросить объяснить один метод, API или ошибку из Console;
- получить наводящую подсказку по текущему шагу;
- сравнить два возможных подхода;
- попросить предложить проверки для уже написанного кода;
- сверить готовую работу с критериями.

Нельзя:

- просить написать готовый `project/script.js`;
- поручать ИИ основную часть или дополнительное задание целиком;
- вставлять сгенерированный код, который вы не писали и не понимаете;
- поручать ИИ описание pull request;
- скрывать использование ИИ.

Самостоятельное исследование в уровне B не означает «попросить ИИ сделать функцию». Можно использовать документацию и просить объяснить отдельный механизм, но реализацию, проверку и интеграцию нужно выполнить самостоятельно.

В описании PR достаточно честно указать инструмент и конкретную помощь. Отдельный отчет об ИИ не нужен.

Самостоятельность проверяется объяснением кода и небольшим изменением по новому условию. Преподаватель может попросить добавить поле, изменить правило валидации, переименовать ключ, изменить временное состояние или исправить один из переходов интерфейса.
